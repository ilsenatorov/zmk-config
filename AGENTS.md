# AGENTS.md

This file provides guidance to coding agents (Claude Code etc.) when working with code in this repository.

## What this is

Config for two personal keyboards. The **TOTEM** (38-key wireless split) runs **ZMK**; the **ErgoDox EZ Glow** (wired, ATmega32u4) runs **QMK** — ZMK has no AVR support, so it cannot run on the ErgoDox. The ErgoDox's `qmk/ergodox_ez/` keymap is its **own** layout — derived from the Oryx layout `xbvqK/nlyNZG` (BASE/GAME/SYM/NUM/MOUSE), not from the TOTEM's. What the two boards *do* share is typing feel: the same home-row mods, the same bilateral hold guard, and the same nine combos, added to the ErgoDox's base layer. See "The ErgoDox EZ (QMK)" below for that side; everything else in this file is TOTEM/ZMK.

A ZMK firmware config repo (created from the `zmk-config-template`) for a **TOTEM** keyboard — a 38-key column-staggered split, wireless (Seeed XIAO BLE) build. It holds only *user config* — keymap, Kconfig overrides, and build matrix — not the ZMK firmware, shield definition or LED widget themselves. Those are pulled in via west:

- ZMK firmware source: `zmkfirmware/zmk` (**unpinned — tracks `main`**; `config/west.yml` sets no `revision` for it, so `defaults: revision: main` applies)
- TOTEM shield definition: `bildermankawasaki/zmk-keyboard-totem` (an external ZMK module — not vendored into this repo)
- Battery/connection LED: `caksoylar/zmk-rgbled-widget` (an external ZMK module; its `main` targets ZMK `main`, so pin both together if ever pinning)

All three are declared in `config/west.yml` and checked out into `.zmk/` (gitignored, not part of this repo) by `west update`.

## Layout

- `config/west.yml` — west manifest. Declares `zmk` (`zmkfirmware`), the `zmk-keyboard-totem` module (`bildermankawasaki`), which provides the `totem_left`/`totem_right` shields, and the `zmk-rgbled-widget` module (`caksoylar`), which provides the `rgbled_adapter` shield and the `&ind_bat`/`&ind_con` behaviors. **All track `main`** (`zmk` via `defaults: revision: main`). Verify behavior/keycode names against ZMK `main`, not a release tag.
- `build.yaml` — GitHub Actions build matrix: board `xiao_ble/nrf52840/zmk` with the shields `totem_left rgbled_adapter` and `totem_right rgbled_adapter`, no extra snippet or cmake args. `rgbled_adapter` maps the XIAO BLE's onboard RGB LED for the widget and enables `CONFIG_RGBLED_WIDGET`; each half blinks its **own** battery level (green/yellow/red) on boot and when `&ind_bat` is pressed. The host can't see the right half's battery (see `totem.conf`); besides the LED, `&bat_type` types both levels as text (see `src/behaviors/` below). `scripts/build.sh` passes the same shield pairs. ZMK Studio support was dropped (no `studio-rpc-usb-uart` snippet, no `-DCONFIG_ZMK_STUDIO=y`, no `&studio_unlock` in the keymap) since it's no longer used.
- `config/totem.keymap` — the keymap (6 layers: `BASE`, `QWERTY`, `SYM`, `NUM`, `ADJ`, `FUN` — see "Editing the keymap" below for the *why*; the file itself, including its header comment with the physical key-position numbering, is the source of truth for the *what*). This overrides the default keymap bundled in the `zmk-keyboard-totem` module — ZMK prefers a `<shield>.keymap` found in `config/` over the shield's own.
- `config/totem.conf` — Kconfig overrides: `CONFIG_ZMK_POINTING=y` (required for the `&mmv`/`&mkp` mouse keys on FUN), `CONFIG_ZMK_SLEEP=y` + `CONFIG_ZMK_IDLE_SLEEP_TIMEOUT=300000` (deep sleep after 5 min idle; the shield's `kscan` has `wakeup-source`, so any keypress wakes it — reconnect just takes a couple seconds), `CONFIG_ZMK_BATTERY_REPORT_INTERVAL=300` (battery sampled every 5 min rather than 60 s, to save power) and `CONFIG_BT_CTLR_PHY_2M=n` (fixes a pairing loop with this host's Intel AX200/AX201 controller). The split battery proxy (`CONFIG_ZMK_SPLIT_BLE_CENTRAL_BATTERY_LEVEL_*`) is **deliberately off**: it adds a second Battery Service, which hits a BlueZ bug that aborts GATT service discovery and causes a pair/disconnect loop. So the host sees only the left half's battery. `CONFIG_ZMK_SPLIT_BLE_CENTRAL_BATTERY_LEVEL_FETCHING` (the left half learning the right's level internally, no extra host-facing service) *is* on, but it's `select`ed by this repo's `Kconfig` for `&bat_type`, not set here.
- `boards/shields/` — for a custom/unreleased shield defined *in this repo* rather than pulled in as a module. Currently just a placeholder (`.gitkeep`); not used for TOTEM since its shield lives in the external module above.
- `zephyr/module.yml` — declares this repo as a Zephyr module (`cmake: .`, `kconfig: Kconfig`, `board_root: .`, `dts_root: .`), so the root `CMakeLists.txt`/`Kconfig`, the bindings under `dts/` and any shields under `boards/` (not currently used) are picked up by the build. CI's `build-user-config.yml` and `scripts/build.sh` (`-DZMK_EXTRA_MODULES`) both load it.
- `src/behaviors/behavior_battery_type.c` + `dts/bindings/behaviors/zmk,behavior-battery-type.yaml` + root `CMakeLists.txt`/`Kconfig` — a custom zero-param behavior, instanced in the keymap as `&bat_type`, that types each half's battery level via the behavior queue (`&kp` taps), e.g. `L87 R64`. `R?` means the left half has no level for the right half (ZMK stores 0 until the first report and resets to 0 on disconnect). The source is only compiled on the central (same gating as ZMK's macro behavior — `behavior_queue.c` doesn't exist on a peripheral); the `Kconfig` symbol `select`s `..._BATTERY_LEVEL_FETCHING` on the central only. Output goes through the host's keyboard layout, so it assumes the host uses QWERTY.
- `.github/workflows/build.yml` — CI: calls ZMK's reusable `build-user-config.yml` workflow, which builds every entry in `build.yaml` and uploads `.uf2` firmware as build artifacts.
- `.github/workflows/draw.yml` + `keymap-drawer/` — CI: calls `caksoylar/keymap-drawer`'s `draw-zmk.yml` on any push touching `config/*.keymap` or `config/west.yml`, regenerating `keymap-drawer/totem.{yaml,svg}` and committing them back. **These two files are generated output — don't hand-edit them.** To refresh locally: `uvx --from keymap-drawer keymap parse -z config/totem.keymap > keymap-drawer/totem.yaml && uvx --from keymap-drawer keymap draw keymap-drawer/totem.yaml > keymap-drawer/totem.svg`.
- `.github/workflows/totem-ergodox-sync.yml` — CI: on any push/PR touching `config/totem.keymap`, warns (doesn't fail the build) if `qmk/ergodox_ez/keymap.c` wasn't touched in the same diff — a non-blocking nudge to check whether the change belongs on both boards. The two keymaps do **not** mirror each other layer-for-layer (see "The ErgoDox EZ (QMK)" below) — only the home-row-mod tuning and the combo set are meant to stay in sync, and there's no automated way to do that across the two formats.
- `.zmk/` — local west workspace (gitignored, disposable). `.zmk/config/` is a thin shim dir holding only a symlink to the real `config/west.yml` — this makes `.zmk` its own west topdir (separate from `config/`) so the vendored `zephyr/` checkout doesn't collide with this repo's own `zephyr/module.yml`. `scripts/build.sh` creates/repairs it automatically; don't edit or commit anything under it.
- `scripts/build.sh` / `scripts/flash.sh` — local build/flash automation, see below.
- `scripts/build-ergodox.sh` / `scripts/flash-ergodox.sh` — the ErgoDox equivalents, see "The ErgoDox EZ (QMK)".
- `firmware/` — build output (`totem_left.uf2`, `totem_right.uf2`, `ergodox_ez_glow.hex`), gitignored.

## Building and flashing firmware

**CI**: GitHub Actions builds on every push and pull request (or manual `workflow_dispatch`); `.uf2` files are attached as workflow artifacts. Good for verifying, too slow for iterating on a keymap.

**Local (fast loop)**: `scripts/build.sh` and `scripts/flash.sh` build inside the same `zmkfirmware/zmk-build-arm:stable` Docker image CI uses — no local Zephyr SDK install needed, just Docker.

```sh
./scripts/build.sh              # builds both halves -> firmware/totem_{left,right}.uf2
SKIP_UPDATE=1 ./scripts/build.sh  # skip `west update`; ~10s incremental rebuild after a keymap-only edit
rm -rf .zmk/build                 # needed after changing the SHIELD list: `-p auto` keeps the cached SHIELD ("Ignored value=...")

./scripts/flash.sh left         # build + flash just the left half
./scripts/flash.sh right
./scripts/flash.sh both         # flash both, one after the other
./scripts/flash.sh left --skip-build   # flash the last build without rebuilding
```

`flash.sh` polls `/run/media/$USER/*`, `/media/$USER/*`, `/media/*`, `/mnt/*` for a mounted UF2 bootloader drive (identified by `INFO_UF2.TXT`), and if none is auto-mounted tries `udisksctl mount` on any unmounted vfat partition; it copies the firmware once the drive appears (up to 60 s per half). Put the target half into bootloader mode when prompted — double-tap its reset button, or (once it's already running this keymap) hold `&mo ADJ` (bottom-right outer key) and tap the half's own bootloader key: position 21 for the left half, position 30 for the right half — the outer pair on the bottom row (`&sys_reset` sits on the inner pair, 22/29, the same way). These are plain bindings, not combos, on purpose: ZMK combos always invoke their behavior with a "local" event source, so a combo can never target the peripheral (right) half — it would silently reset the central (left) half instead, no matter which positions it listed. A direct binding on the key itself carries that key's real originating half.

## Editing the keymap

Edit `config/totem.keymap` directly. Layer indices are `#define`d at the top (`BASE`/`SYM`/`NUM`/`ADJ`/`FUN`); each `bindings` block's physical layout is documented by the TOTEM shield's `totem-layout.dtsi` (in the `zmk-keyboard-totem` module) — rows read top-to-bottom, left-half then right-half, with the thumb cluster last. **The keymap's own header comment is the authoritative, current physical key-position numbering** (0-37) and the `KEYS_L`/`KEYS_R`/`THUMBS` groupings derived from it — don't re-derive or duplicate that numbering here; read it there. The home-row-mod positional guard depends on it, so keep the comment in sync if the shield layout ever changes.

Layer design, and *why* it is the way it is (for the actual bindings, read the layer itself — this is only the non-obvious reasoning behind them):

- **BASE** — [Graphite](https://github.com/rdavison/graphite-layout) with timer-less home-row mods (`hml`/`hmr`: `balanced` flavor, 280 ms term, `require-prior-idle-ms`, a bilateral `hold-trigger-key-positions` guard and `hold-trigger-on-release`). The guard is deliberate: `Super`+a left-hand letter must take GUI from the **right** hand (`I`) and vice-versa, otherwise the hold resolves as a tap. The left thumb's `&mt LGUI ESC` is a plain mod-tap with no positional guard, so it is the other way to get `Super` with left-hand keys. Graphite has 31 main-block keys and the TOTEM 30, so its 11th-column `,` takes the bottom-row `-` slot (position 29); `-` comes from the `m`+`c` combo, SYM or NUM. Shifted punctuation is the plain US pairs, not Graphite's custom ones. The combos kept their QWERTY-era *positions*, so several now sit on common Graphite bigrams (`rt`, `ts`, `ha`, `ea`, `ei`) — watch for misfires.
- **QWERTY** — the old QWERTY base (with the same home-row mods), kept as a fallback while learning Graphite. Toggled with `&tog QWERTY` on ADJ position 5. It must stay at index 1, directly above BASE, so SYM/NUM/ADJ/FUN still override it; only the 30 alpha keys are set. Combos list `layers = <BASE QWERTY>` because ZMK only fires a combo when the *highest* active layer is in its list.
- **SYM** (held on the **left** thumb, `Space`) — symbols, with the same home-row mods as BASE on the home row (`hml`/`hmr` wrapping `! * / =` and `( ) ; "`, so e.g. `Ctrl+/` works without leaving the layer); everything else is plain `&kp`. Openers sit on the right index column and closers on the right middle column.
- **NUM** (held on the **right** thumb, `Tab`) — a real number row, plain (non-hold-tap) modifiers `GUI`/`Alt`/`Ctrl`/`Shift` plus `-` on the **left** home row, and navigation on the right: `PgUp` and the arrows (`←↑↓→`) on the home row, `PgDn`/`Home`/`End` below. The plain modifiers let any digit or navigation key be chorded without leaving the layer. NUM's three **left thumb** keys send `Super`, `Super+Shift` and `Super+Ctrl` directly, so Hyprland's window bindings on the arrows — focus (`Super+arrow`), move window (`Super+Shift+arrow`) and merge into group (`Super+Ctrl+arrow`) — are one thumb plus one right-hand finger. (These thumbs originally existed for `Super+1..0` workspace switching; Hyprland's workspaces have since moved to `Super+Q..P` on the letter row, which BASE reaches directly — the unguarded `&mt LGUI ESC` thumb or the `;` home-row mod supplies `Super`.) `&mo FUN` also lives on NUM's left pinky (position 20), so FUN nests under NUM too — hold `Tab`, hold the pinky key, tap a top-row key.
- **ADJ** — Bluetooth, output and media, plus `&ind_bat` (position 13) and `&ind_con` (position 23), which blink the LED widget's battery and connection status on both halves, and `&bat_type` (position 24), which types both halves' battery levels into the focused window. Reached by holding `&mo ADJ` on the bottom-right outer key (momentary, not toggled); position 31 stays `&trans` on ADJ so releasing that key always exits. `&bootloader`/`&sys_reset` are plain keys on the bottom row (outer pair = boot, inner pair = reset, mirrored per half), deliberately not combos — see "Building and flashing firmware" for why.
- **FUN** — F1-F12 and mouse keys, reached directly from BASE by holding the left pinky key (position 20, `&mo FUN`) or nested under NUM (see above). F1-F10 mirror NUM's number row exactly (same top-row positions as `1`-`0`); F11/F12 go down the right inner column instead — F11 on the home row under F6, F12 on the bottom row under that. The rest of the right home row is mouse movement in the same order as NUM's arrows, the bottom row under it is scrolling in the same order (`&msc`), and the right thumbs `Bspc`/`Tab`/`Del` become left/right/middle click (`&mmv`/`&msc`/`&mkp`, which need `CONFIG_ZMK_POINTING`). The clicks are only usable when FUN comes from BASE, since nesting under NUM keeps `Tab` held.

`&lt` is overridden globally with `quick-tap-ms` (upstream has none, so hold-to-repeat on Space/Esc/Tab would not work). Its flavor stays `tap-preferred` on purpose: with `balanced`, rolling from `Space` into the next word's first letter resolves as a hold and fires SYM.

No working Docker (daemon stopped, or the user not in the `docker` group)? Without a build you can still validate a keymap edit statically: check 38 bindings per layer, and that every keycode and behavior resolves against `app/include/dt-bindings/zmk/keys.h` and `app/dts/behaviors/` on ZMK `main`. `uvx --from keymap-drawer keymap parse -z config/totem.keymap` is also a real parse and will fail on malformed devicetree.

## Adding another ZMK keyboard to this repo

1. If it's a custom/unreleased shield, add its definition under `boards/shields/<shield_name>/`; if it's an existing community shield, add it as a module in `config/west.yml` instead (see how TOTEM is set up above).
2. Add the keymap as `config/<shield_name>.keymap` (and `config/<shield_name>.conf` for Kconfig overrides).
3. Add a `board`/`shield` (or `include:`) entry in `build.yaml`.

## The ErgoDox EZ (QMK)

Not built via west/Zephyr at all — QMK has its own toolchain, and this board doesn't use ZMK Studio, west, or `config/`.

**The ErgoDox runs its own layout, not a port of the TOTEM's.** `keymap.c` is derived from the Oryx layout `xbvqK/nlyNZG` — five layers, `_BASE`/`_GAME`/`_SYM`/`_NUM`/`_MOUSE`, with the ErgoDox's own numpad and mouse/RGB layers that the TOTEM has no equivalent for. Layers `_SYM` through `_MOUSE` are carried over from the Oryx source export verbatim, except that `_MOUSE`'s RGB controls were cut down to a single on/off key (`RM_TOGG`); `_BASE` was modified to add home-row mods and combos, and its alphas switched to Graphite, placed exactly as on the TOTEM. `_GAME` pins all 30 alphas to plain QWERTY (no mods), so it keeps WASD and doubles as the QWERTY fallback; anything left `KC_TRANSPARENT` there would fall through to Graphite. The Oryx per-key RGB `ledmap` is **not** carried over — lighting is a custom effect (see below). When re-exporting from Oryx, diff against the export rather than rewriting by hand.

What *is* shared with the TOTEM, and what the sync workflow is nudging about: the home-row-mod flavour and timing, the bilateral hold guard, and the nine combos (`config/totem.keymap`'s `combos` block is the reference set — Caps Word, `_`, `-`, `:`, `?`, Home, End, `'`, `"`), plus the Graphite alpha block. ErgoDox combos are keycode-based, so they name the Graphite letter on each position; moving a letter means updating them. Layer *design* changes on the TOTEM are expected to trip the warning without being ported; that's fine.

- `qmk/ergodox_ez/` — the QMK "keymap folder": `keymap.c` (five `LAYOUT_ergodox_pretty` layers, the `chordal_hold_layout` bilateral-mod guard — which exempts the left thumb's `MT(MOD_LGUI, KC_ESCAPE)` Super key, since it's chorded with left-hand keys constantly (`Super+1..6`, `Super+Q`) and the guard turned every such chord into a tap — the `NUMF()` tap-digit/hold-F-key number row, nine combos gated to `_BASE` by `combo_should_trigger()`, and a `keyboard_post_init_user()` that pins the RGB mode), `rgb_matrix_user.inc` (the `LAYER_GLOW` effect — the only RGB effect built: a warm white on `_BASE` and a pastel two-hue gradient on `_SYM`/`_NUM`/`_MOUSE`, each with a slowly drifting rainbow revealed under every pressed key, and that rainbow itself at full brightness as `_GAME`'s color; colors, per-layer brightness and the `rainbow`/`reveal` flags live in its `layer_glow[]` table, indexed in `enum layers` order since the enum isn't visible there), `config.h` (tap-hold/combo tuning, and `#undef`s for every stock RGB animation the board enables), `rules.mk` (feature flags), `keymap.json` (`{"modules": ["zsa/oryx", "zsa/defaults"]}` — this, not an `ORYX_ENABLE` flag, is what keeps ZSA's Keymapp/live-training working on this firmware branch; `ORYX_ENABLE` doesn't exist here and is silently ignored if set).
- Built against **ZSA's QMK fork, branch `firmware25`** (`https://github.com/zsa/qmk_firmware`) — the same branch Oryx itself compiles from — not mainline QMK, because the fork carries the `zsa/oryx` community module and matches Oryx's `CHORDAL_HOLD`/`FLOW_TAP` behaviour. Pin changes deliberately; don't float to a newer `firmwareNN` branch without re-checking flash usage.
- **Flash is the hard constraint on every future edit.** `LAYER_STATE_8BIT` caps layers at 8 (this keymap uses 5) and the ATmega32u4 has 32256 bytes total; the last build compiled to **23356 bytes — 8900 free (72% used)**. That headroom exists only because `qmk/ergodox_ez/config.h` `#undef`s all the stock RGB Matrix animations (50 `#undef` lines) the upstream `keyboards/zsa/ergodox_ez/config.h` enables (with them the keymap sat at 31706 bytes, 550 free). Re-enabling animations is the fastest way back to a full chip. Check the build's printed size line after any feature change (`scripts/build-ergodox.sh` also greps and warns if free space drops under 512 bytes).
- `.github/workflows/draw-ergodox.yml` + `keymap-drawer/ergodox_ez.{yaml,svg}` — CI: on any push touching `qmk/ergodox_ez/keymap.c`, shallow-clones the ZSA fork (no submodules — those are only needed to *build* firmware, not to convert the keymap), runs `qmk c2json` to turn `keymap.c` into a QMK `keymap.json`, then `keymap-drawer` parses that into `ergodox_ez.yaml` and draws `ergodox_ez.svg`, committing both back. No reusable `draw-qmk.yml` exists upstream (unlike ZMK's `draw-zmk.yml`), so this workflow drives the CLI directly. **The `.yaml`/`.svg` are generated output — don't hand-edit them**; the intermediate `.json` is not committed. The physical layout is drawn from mainline QMK's `ergodox_ez/glow` (`-k ergodox_ez/glow` — passed explicitly since keymap-drawer's automatic QMK-keyboard lookup only knows mainline keyboard names, not the ZSA fork's `zsa/ergodox_ez/m32u4/glow` id used to parse the layers) since the physical layout is identical between the fork and mainline. To refresh locally, see the same `qmk c2json` + `keymap parse -q` + `keymap draw -k ergodox_ez/glow` steps as in the workflow file — needs Docker (`qmkfm/qmk_cli` image) or a local `qmk` install to run `c2json`.
- `scripts/build-ergodox.sh` — Docker build (`qmkfm/qmk_cli` image), mirrors `scripts/build.sh`'s structure. Clones `zsa/qmk_firmware` into `.qmk/` (gitignored) and initializes only the `lib/lufa` and `modules/zsa` submodules (not the full submodule set — that pulls in ChibiOS/pico-sdk/lvgl for nothing on AVR). `SKIP_UPDATE=1` skips the fetch for a fast keymap-only rebuild. Sets `GIT_CEILING_DIRECTORIES` to stop git's repo-discovery from walking up past the repo root — needed because `.qmk` is nested inside this checkout.
  ```sh
  ./scripts/build-ergodox.sh              # -> firmware/ergodox_ez_glow.hex
  SKIP_UPDATE=1 ./scripts/build-ergodox.sh  # fast rebuild after a keymap-only edit
  ```
- `scripts/flash-ergodox.sh` — the ErgoDox EZ uses the **Teensy HalfKay bootloader, not a UF2 drive** (unlike the TOTEM), so this polls for the HalfKay USB device (`16c0:0478`) instead of a mount point, then flashes with `wally-cli` or `teensy_loader_cli`. Needs ZSA's udev rules (`/etc/udev/rules.d/50-zsa.rules`) to flash without root.
- Bootloader entry: **the physical reset button** (paperclip hole, top-right of the right half). This keymap has no `QK_BOOT` key on any layer — neither did the Oryx layout it came from, so this is how the board has always been flashed. There is now flash to spare for one if wanted.
